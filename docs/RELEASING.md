# Releasing

Releases are cut from **annotated semver tags only**. `main` stays
always-green and always-deployable, and merging to `main` deploys to **QA**
and to nowhere else.

The tag decides which environment it is a release *to*:

| Tag | Channel | Environment | Gate |
|---|---|---|---|
| `v0.2.0-rc.1` | `staging` | Staging | none |
| `v0.2.0` | `prod` | Production | one human approval |

One pipeline, one guard, one set of release notes, two destinations — so the
path to production is the path staging has already rehearsed, rather than one
nobody has run before the day it matters.

**No environment can be released to until its URL is recorded.** The pipeline
refuses, before anything is published, whenever the target channel's entry in
[`deploy/hetzner/environments.env`](../deploy/hetzner/environments.env) is
empty — for staging exactly as much as for production.

Today **all three are empty**, so a release candidate is refused too. That is
correct rather than a gap: nothing is provisioned yet, and a channel moved to
an environment nobody can probe is a deploy nobody checked. Filling the URL in
is the last step of provisioning a host, and it is what makes releases to it
possible. See [ENVIRONMENTS.md](ENVIRONMENTS.md).

## The pipeline

`.github/workflows/release.yml`, on every pushed `vMAJOR.MINOR.PATCH*` tag:

1. **Guard** — the tag must be annotated (`git cat-file -t` says `tag`), its
   name strict SemVer 2.0.0 with a `v` prefix, and its commit reachable from
   `origin/main`. A lightweight tag, a tag on unmerged work, or a non-semver
   name is refused with the fix named. And if a GitHub Release for the tag
   already exists, the tag must still point at the commit that Release
   records: re-releasing the same commit is the rollback and passes, while a
   tag that has been **moved** is refused before anything ships — a published
   version names one commit forever. The rule lives in
   [`scripts/release_guard.sh`](../scripts/release_guard.sh); its test suite
   runs first on every release, together with the notes generator's.
2. **Verify** — the full CI matrix on the tagged commit, by calling `ci.yml`
   via `workflow_call` (the same jobs PRs run, defined once).
3. **Approve** — for a final tag only, and only if production exists. A
   required review on the `production` GitHub Environment. Everything else in
   this pipeline is automatic by design; this is the one gate, because
   production is the only environment where being wrong costs something that
   cannot be re-run.
4. **Publish** — both images are built with the tag stamped in, pushed to
   GHCR under an immutable `sha-<commit>` tag, and then **the published
   artefact is run and made to say its own version**. A build whose stamp did
   not land fails here, having moved no channel, and sits in the registry
   addressable by commit for whoever wants to know why.
5. **Move the channel** — `imagetools create` re-points `:staging` or
   `:prod` at the proven digest. **This is the deploy.** Every host tracking
   that channel converges within a minute, with no instruction from CI.
6. **GitHub Release** — published from the tag with notes generated by
   [`scripts/release_notes.sh`](../scripts/release_notes.sh): commits since
   the previous *release*, grouped by Conventional Commit type, breaking
   changes first, and the commit the version was cut from — which is what the
   guard reads back on any later run of the same tag. Publishing is
   idempotent, because re-releasing a tag is the rollback. A pre-release tag
   is published as a pre-release.
7. **Probe** — `GET /healthz` and `GET /readyz` on that environment's URL from
   [`deploy/hetzner/environments.env`](../deploy/hetzner/environments.env).
   Both must answer 200 **and report the version being released**: a 200 alone
   would be answered just as happily by the previous container. The retries
   cover the whole pull-based path — up to a minute before the host's timer
   fires, then the pull, the rollout and the schema migration on boot — about
   five minutes, after which a refusal is a refusal. A release that does not
   answer, answers as another version, or was never probed is a **failed
   release** and the run says so.

## What the deployment looks like

The application runs in containers on a Hetzner VPS, behind a Caddy reverse
proxy, behind Cloudflare. [ENVIRONMENTS.md](ENVIRONMENTS.md) is the full
picture; the parts that bear on releasing:

| Path | Container |
| --- | --- |
| `/api/…`, `/healthz`, `/readyz` | the Go API |
| everything else | the Astro web frontend |

The API is not published on a host port in any environment — Caddy is the
only thing that reaches it, and the frontend reaches it privately across the
compose network.

**CI cannot reach a host.** There is no SSH key in this repository's secrets,
no deploy credential for a VPS, and no inbound endpoint on one. CI writes to
the registry; hosts read from it; neither can reach the other. What a release
does is move a tag.

**Every environment is pinned by digest.** A channel tag is what an
environment *tracks*; the digest is what it *runs*. "What is running in
staging" therefore has one answer that cannot drift under a tag someone
moved.

**Cloudflare Containers is retired** and nothing deploys there.
`wrangler.jsonc` and `deploy/cloudflare/` remain, still validated by CI, as
the reference implementation of the editorial rate limit — which means the
deployment currently has **no editorial rate limit in force**. Porting it to
Go middleware is required before anything is publicly reachable
([ENVIRONMENTS.md](ENVIRONMENTS.md)); deleting the Cloudflare path is what
that unblocks.

## Semver discipline (pre-1.0)

While the version is `0.x.y`, the contract is:

- **minor** (`v0.2.0`): new user-visible behaviour — features, new endpoints,
  new screens. Pre-1.0, breaking changes are allowed here too, but each one is
  named in the notes (Conventional Commit `!`).
- **patch** (`v0.1.1`): fixes only. Nothing new, nothing removed.
- **pre-release** (`v0.2.0-rc.1`): a candidate for the version it names,
  released to staging. Cut as many as it takes; each is a real release with
  real notes, and the final tag is cut from the same commit as the candidate
  that passed.

`v1.0.0` will mean the public contract holds: the reader API and URL structure
are stable, the invariant set (I-1…I-5) is frozen as documented, and from then
on breaking changes require a major version. Until then, 0.x says exactly what
it says everywhere: the ground may still move.

## Cutting a release

Tag the tip of `main` (never an unmerged branch), annotated, and push the tag
— that push is the release:

```sh
git fetch origin

# to staging
git tag -a v0.2.0-rc.1 -m "release candidate v0.2.0-rc.1" origin/main
git push origin v0.2.0-rc.1

# to production, once it exists, from the commit the candidate proved
git tag -a v0.2.0 -m "release v0.2.0" origin/main
git push origin v0.2.0
```

Watch the `release` run in Actions. The run summary carries the generated
notes and the probe verdict. Then, from anywhere:

```sh
sh scripts/env_status.sh
```

which answers what each environment is actually serving, over plain HTTPS,
with no credentials.

## Rehearsal (dry run)

Actions → **release** → *Run workflow* → pick the **tag** under "Use workflow
from" → leave **dry_run** checked. Everything runs — guard, the full CI
matrix, note generation — but no images are published, no channel moves and
no Release is created. The workflow refuses to run from a branch ref.

## One-time setup

Far less than the previous deployment needed, because the registry is the
only thing CI writes to and it authenticates with the token GitHub already
issues each run.

### 1. Nothing, for the registry

`publish.yml` pushes to `ghcr.io/<this repository>` using the built-in
`GITHUB_TOKEN` with `packages: write`. There is no secret to create and none
to rotate.

Make sure the two packages (`…/api`, `…/web`) are readable by whatever pulls
them. The deployment hosts log in with a read-only PAT
(`read:packages`) — see [ENVIRONMENTS.md](ENVIRONMENTS.md).

### 2. The `production` GitHub Environment

Settings → Environments → **New environment** → `production` → add **required
reviewers**.

This is the approval gate on step 3. Who may approve a production release is
configured there, deliberately, rather than in any file this repository can
change. Until it exists, a final tag is refused anyway (there is no
production), so this can wait until the production host does.

### 3. The environment URLs

[`deploy/hetzner/environments.env`](../deploy/hetzner/environments.env),
committed, in a pull request. It is what the probe reads and what
`env_status.sh` reports on.

It is a file rather than a settings screen on purpose, and for the same reason
`wrangler.jsonc` was: a value that lives only in a dashboard has no history,
no review, and no diff when it changes.

An empty value means that environment does not exist yet — a real state, and
the one production is in.

### 4. Per-environment application secrets

These live on the deployment host, at `/etc/apivo/<env>/api.env` (mode 0600)
and `web.env`, read by the Docker daemon as each service's `env_file`. They
are **never** repository secrets: a release does not read GitHub's, and a
`DATABASE_URL` set there reaches nothing.

| Key | Value |
| --- | --- |
| `DATABASE_URL` | Production: its own Supabase (EU) connection string, **with `sslmode=verify-full`**. QA and Staging: the Postgres container on the host, with `sslmode=require` (the free tier is one Supabase project and it is production's — see [ENVIRONMENTS.md](ENVIRONMENTS.md)). |
| `JWKS_URL`, `JWT_AUDIENCE` | Supabase Auth. Production points at its own project; QA and Staging have no project of their own, so leaving these empty unmounts the editorial routes and keeps serving readers. |
| `PUBLIC_SUPABASE_URL`, `PUBLIC_SUPABASE_ANON_KEY` | The matching half, in `web.env`. Not credentials. |
| `TRANSLATION_*` | The provider and budget, once decided. The caps are real money and are per-environment — QA runs every merge, so if it translates at all it carries a small cap of its own. |

**`sslmode` is load-bearing.** Every `DATABASE_URL` example in this repository
ends in `sslmode=disable`, because every example describes a local Postgres on
a loopback address — so the value most likely to be copied into a deployment
is the one that must never be there. Every environment runs `APP_ENV=prod`,
and the api **refuses to start** on a URL whose `sslmode` permits an
unencrypted session (`disable`, `allow`, `prefer`, or absent). Use
`verify-full` against Supabase, which also proves the server is the one it
claims to be:

```
postgres://USER:PASSWORD@HOST:5432/postgres?sslmode=verify-full
```

## Rollback

Rolling back is **re-releasing the previous tag** — there is no separate
mechanism, so the rollback path is exactly as tested as the release path:

Actions → **release** → *Run workflow* → pick the previous good tag →
**uncheck** `dry_run` → run. The guard, verification, publish and probe all
run again, the channel moves back, and every host tracking it converges on
its own within a minute. The footer and `apivo version` report the rolled-back
tag, honestly.

The tag already has a GitHub Release, and that is expected: its notes are
updated rather than re-created, and the probe still runs and still asserts
that the version now serving is the one just released.

There is also a **last line of defence on the host itself**: a rollout whose
containers do not come up healthy, or that comes up on the wrong image or
serving the wrong version, is rolled back by the reconciler to the digest that
was serving, before any of this is needed. The channel still points at the
broken build, so the next tick tries it again — fix it forward, or move the
channel back with the workflow above.

**Never move a released tag.** Re-pointing `v0.1.0` at a newer commit and
force-pushing would ship different code under a version the world has already
seen, described by release notes written for the old commit. The guard refuses
it: it compares the tag's commit against the commit recorded on the published
Release and stops the run before anything ships. If the released code was
wrong, roll back to the previous tag and cut a new version — that is what
patch releases are for.

## Pinned versions of the ledger

The cashback product runs an adopted open-source ledger, **Blnk**
([ADR-0002](adr/0002-cashback-money-substrate.md)), as a sidecar. Two versions
are pinned for it, and they are pinned together:

| What | Where | Pinned as |
| --- | --- | --- |
| Blnk Go SDK | `go.mod` | `github.com/blnkfinance/blnk-go v1.3.0` |
| Blnk server image | `docker-compose.yml`, `.github/workflows/ci.yml` (`BLNK_IMAGE`), `deploy/hetzner/compose/docker-compose.cashback.yml`, `deploy/k8s/cashback/blnk-deployment.yaml` | `jerryenebeli/blnk:0.15.2@sha256:796518b1…` |
| Redis image | the same four files | `redis:7.2.4-alpine@sha256:c8bb255c…` |

**The container images are pinned by DIGEST, not by tag** — the form is
`repo:tag@sha256:…`, which Docker resolves by digest and a reviewer reads by
version. The tag is documentation; the digest is the contract. A tag is
mutable, and the ledger is the one component in this system where a silent
retag would change the binary that moves members' money, with no diff and no
review.

The Redis version tracks what Blnk's own compose file runs (7.2.x) rather than
the newest release, so no environment discovers a version skew the others do
not have.

**Why the SDK is pinned to an exact version, and not to a range.** The ledger
is the only component in this repository that can silently produce a wrong
number instead of an error. A floating SDK would mean the client that posts
money can change between a green CI run and a deploy, with no commit to point
at. Blnk is also a modest project rather than a decade-old standard — ADR-0002
names that adoption risk explicitly — so the version in force has to be a fact
in the repository, not whatever resolved that morning.

**Why the two are pinned together.** The SDK speaks a wire format the server
defines. `blnk-go` v1.3.x is written against Blnk core 0.15.x — its own source
carries the compatibility notes — and a bump on one side without the other is
a mismatch nothing in the build would notice until a transfer failed. So the
compose file, the CI job and `go.mod` name their versions explicitly and a
bump touches all of them in one commit.

**Bumping either version:**

1. Change `go.mod` (`go get github.com/blnkfinance/blnk-go@vX.Y.Z`) and the
   image reference — **tag and digest together** — in all four files listed
   above, in one commit. Read the new digest from the registry
   (`docker buildx imagetools inspect jerryenebeli/blnk:<tag>`) rather than
   from a local pull, so the pin is the multi-architecture index and does not
   quietly commit a deployment to one architecture.
2. `scripts/spikes/ledger_sdk/` fails at compile time if the SDK dropped or
   renamed something the ledger port depends on — including `Reference`, the
   field the exactly-once payout guarantee (C-5) rests on.
3. The `cashback` CI job must be green: it migrates the ledger schema, starts
   the server and runs the suite against it. **That job is the verification of
   record** — Docker Desktop is unavailable on the founder's machine, so no
   ledger bump can be validated locally, and a PR that bumps one must say so.
4. Read Blnk's release notes for schema migrations. `blnk migrate up` runs
   against the same Postgres as the application; a ledger migration is a
   schema change to the production database like any other.

## Migrations are forward-only

The api container migrates the schema on boot (`internal/platform/db`). The
discipline:

- Migrations only ever roll **forward**. There are no down-migrations, and a
  release never reverses one.
- A rollback therefore re-deploys **old code against the migrated schema**.
  The append-only design is what makes that safe: migrations add tables,
  columns and constraints; they do not repurpose or drop what running code
  reads. Write every migration so the previous release still runs against the
  result.
- The reconciler's rollout timeout allows for a long migration on boot
  (`APIVO_WAIT_TIMEOUT`, 180s by default). A migration that will take longer
  than that on a real dataset needs the timeout raised in
  `/etc/apivo/<env>/stack.env` before the release, not after it has been
  rolled back for being slow.
