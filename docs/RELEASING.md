# Releasing

Releases are cut from **annotated semver tags only**. Pushing `v0.1.0` is
the release act; nothing else deploys production. `main` stays always-green
and always-deployable — but merging to `main` never deploys anything.

The pipeline (`.github/workflows/release.yml`) runs on every pushed
`vMAJOR.MINOR.PATCH` tag:

1. **Guard** — the tag must be annotated (`git cat-file -t` says `tag`) and
   its commit reachable from `origin/main` (`git merge-base --is-ancestor`).
   A lightweight tag, a tag on unmerged work, or a non-semver name is
   refused with the fix named. The rule lives in
   [`scripts/release_guard.sh`](../scripts/release_guard.sh); its test
   suite (`scripts/release_guard_test.sh`) runs first on every release.
2. **Verify** — the full CI matrix on the tagged commit, by calling
   `ci.yml` via `workflow_call` (the same jobs PRs run, defined once).
3. **Stamp** — the tag is written to a git-ignored `VERSION` file in the
   build context; the Dockerfile reads it into
   `-ldflags "-X main.version=…"`. The workflow builds the api image and
   fails unless `apivo version` prints the tag — the stamp is proven, not
   assumed. The web container receives the tag at request time as
   `PUBLIC_APP_VERSION` and renders it in the footer's fine print.
4. **Deploy** — `npx wrangler deploy` with the committed `wrangler.jsonc`
   (both containers, EU jurisdiction), plus
   `--var PUBLIC_APP_VERSION:<tag>`.
5. **GitHub Release** — created from the tag with notes generated by
   [`scripts/release_notes.sh`](../scripts/release_notes.sh): commits since
   the previous semver tag, grouped by Conventional Commit type, breaking
   changes first.
6. **Probe** — `GET /healthz` and `GET /readyz` on the URL in the
   `RELEASE_HEALTH_URL` repository variable, with retries for container
   cold start. A release that does not answer is a **failed release** and
   the run says so. If the variable is unset the probe is skipped with a
   loud warning in the run summary — never silently.

## Semver discipline (pre-1.0)

While the version is `0.x.y`, the contract is:

- **minor** (`v0.2.0`): new user-visible behaviour — features, new
  endpoints, new screens. Pre-1.0, breaking changes are allowed here too,
  but each one is named in the notes (Conventional Commit `!`).
- **patch** (`v0.1.1`): fixes only. Nothing new, nothing removed.

`v1.0.0` will mean the public contract holds: the reader API and URL
structure are stable, the invariant set (I-1…I-5) is frozen as documented,
and from then on breaking changes require a major version. Until then, 0.x
says exactly what it says everywhere: the ground may still move.

## Cutting a release

Tag the tip of `main` (never an unmerged branch), annotated, and push the
tag — that push is the release:

```sh
git fetch origin
git tag -a v0.1.0 -m "release v0.1.0" origin/main
git push origin v0.1.0
```

Watch the `release` run in Actions. The run summary carries the generated
notes and the probe verdict.

## Rehearsal (dry run)

Actions → **release** → *Run workflow* → pick the **tag** under "Use
workflow from" → leave **dry_run** checked. Everything runs — guard, the
full CI matrix, version stamping with its proof, the wrangler
configuration validation, note generation — but nothing deploys and no
Release is created. The workflow refuses to run from a branch ref.

## One-time setup

The deploy authenticates with two repository **secrets** (Settings →
Secrets and variables → Actions → Secrets), created once by the founder:

| Secret | Value |
| --- | --- |
| `CLOUDFLARE_API_TOKEN` | An API token scoped to the account with the *Workers Scripts: Edit* and *Containers: Edit* permissions (Cloudflare dashboard → My Profile → API Tokens). |
| `CLOUDFLARE_ACCOUNT_ID` | The account id shown on the Cloudflare dashboard's Workers overview. |

The workflow fails before deploying, naming the missing secret, if either
is unset — it never invents placeholder values.

The probe reads one repository **variable** (same page, Variables tab):

| Variable | Value |
| --- | --- |
| `RELEASE_HEALTH_URL` | The base URL under which the deployed service answers `GET /healthz` and `GET /readyz` with 200. |

Until it is set, every release warns loudly that nothing verified the
deployment came up. Note the public Cloudflare hostname routes to the web
container, which does not serve these endpoints today — point the variable
at wherever the api's health endpoints are reachable, and leave it unset
(accepting the warning) until such an address exists.

## Rollback

Rolling back is **re-deploying the previous tag** — there is no separate
mechanism, so the rollback path is exactly as tested as the release path:

Actions → **release** → *Run workflow* → pick the previous good tag →
**uncheck** `dry_run` → run. The guard, verification, stamp and probe all
run again; the footer and `apivo version` report the rolled-back tag,
honestly.

## Migrations are forward-only

The api container migrates the schema on boot (existing behaviour,
`internal/platform/db`). The discipline:

- Migrations only ever roll **forward**. There are no down-migrations, and
  a release never reverses one.
- A rollback therefore re-deploys **old code against the migrated schema**.
  The append-only design is what makes that safe: migrations add tables,
  columns and constraints; they do not repurpose or drop what running code
  reads. Write every migration so the previous release still runs against
  the result.
